# 작업 절차

이 저장소에서 일하는 모든 AI(Claude Code, Codex)와 팀원이 따르는 절차.

## 1. 문서 지도

| 문서 | 용도 | 누가 바꾸나 |
|---|---|---|
| `docs/requirements.md` | 과제가 요구한 것 | 사람만 |
| `docs/design.md` | 설계, 확정/미정 결정 목록 | 확정은 사람, AI는 `제안:`만 추가 |
| `docs/tasks.md` | 작업 단위와 완료 기준 | AI·사람 (상태 변경, 하위 작업 추가) |
| `docs/status.md` | 현재 상태 + 인계 기록 | 세션 끝날 때마다 갱신 |
| `docs/learning.md` | 학습 확인 노트 | 사람이 직접 정리 |
| `docs/workflow.md` | 이 문서 | 사람만 |

읽는 순서: `status.md` → `tasks.md`(현재 작업) → `design.md`(관련 절) → 필요하면 `requirements.md`

## 2. 두 AI 역할

`[미정]` → design.md D16

제안: 작업마다 구현 담당과 검증 담당을 다른 AI로 나눈다. 같은 AI가 만들고 채점하지 않게 하려는 것.
- 예: Claude Code 구현 → Codex 검증, 다음 작업은 반대로
- 담당은 `status.md` "담당" 칸에 적는다.

## 3. 한 작업의 사이클

```
작업 선택 → 구현 → 검증 → 수정 → 학습 확인 → 상태·인계 기록 → 커밋
                      ↑______|
```

### ① 작업 선택
- `tasks.md`에서 `대기` 상태이고 선행 결정이 모두 확정된 작업 **하나**를 고른다.
- `진행 중`으로 바꾸고, `status.md` 현재 상태를 갱신한다.

### ② 구현 (구현 담당 AI)
- 작업 범위 밖의 파일은 건드리지 않는다.
- 설계상 결정이 필요한 지점을 만나면 **멈추고**:
  - `design.md` 결정 목록에 D 항목을 추가하거나 기존 항목에 `제안:`을 단다.
  - 사람에게 묻는다. 임시로 정해야만 진행할 수 있으면, 코드에 `// TODO(Dxx): 임시` 주석을 달고 인계 기록에 남긴다.
- 완료 기준에 맞는 테스트를 같이 작성한다.

### ③ 검증 (검증 담당 AI 또는 사람)
- 완료 기준을 한 줄씩 확인하고 결과를 남긴다(통과 / 실패 + 이유).
- 테스트 명령을 직접 실행한다. "통과할 것 같다"는 검증이 아니다.
- 화면 작업은 브라우저에서 확인한 시나리오를 적는다.
- 확인 항목: 요구사항 ID 충족, 미정 사항을 몰래 확정하지 않았는지, 범위 밖 변경이 없는지

### ④ 수정
- 검증에서 나온 실패만 고친다. 고친 뒤 ③을 다시 한다.
- 같은 문제로 두 번 이상 실패하면 사람에게 넘긴다.

### ⑤ 학습 확인 (사람)
- `learning.md`에서 해당 작업의 질문에 **AI 도움 없이 자기 말로** 답을 적는다.
- 막히면 AI에게 설명을 요청하고, 다시 자기 말로 고쳐 적는다.
- 핵심 코드 몇 줄을 가리키며 "이 줄이 왜 필요한가"를 설명할 수 있으면 통과.

### ⑥ 상태·인계 기록
- `tasks.md` 상태를 `완료`로 바꾼다.
- `status.md` 현재 상태를 덮어쓰고, 인계 기록을 템플릿대로 맨 위에 추가한다.

### ⑦ 커밋
- `[확정]` 각자 자기 브랜치에서 작업하고 커밋·푸시도 거기에만 한다. main에는 직접 푸시하지 않는다. (D19)
- `[미정]` main에 무엇을 어떻게 올릴지(비교 기준, PR 여부)

**브랜치 이름**: `<type>/<작업ID>-<짧은-설명>` (소문자, 단어는 `-`로 연결)
- 예: `docs/T00-workflow-setup`, `feat/T03-dom-to-vnode`, `fix/T06-patch-text-node`, `test/T10-phase1-edge-cases`
- 작업 하나 = 브랜치 하나가 기본. 작은 작업 여러 개를 묶을 땐 대표 ID 사용

**커밋 메시지**: Conventional Commits — `<type>(<작업ID>): <요약>`
- 예: `feat(T03): DOM을 VNode로 변환하는 함수 추가`
- 작업 하나당 커밋 하나가 기본, 필요하면 나눠도 됨

**type 목록**
| type | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 변경 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `style` | CSS, 포맷팅 |
| `chore` | 설정, 의존성 등 기타 |

## 4. 공통 금지 사항
- `requirements.md`, `workflow.md` 임의 수정
- 미정 결정을 확정처럼 문서나 코드에 쓰기
- 외부 프레임워크(React, Vue 등) 사용 (R-TECH-02)
- 테스트를 실행하지 않고 완료 처리
- 세션을 끝낼 때 `status.md` 갱신 안 하기

## 5. 플러그인과의 관계
- oh-my-claudecode, Superpowers 같은 플러그인을 써도 **기준 문서는 `docs/`**다.
- 플러그인이 별도 계획/스펙 파일을 만들면, 그 내용을 `tasks.md`와 `design.md`에 반영한 뒤 진행한다.
