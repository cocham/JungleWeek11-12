# 작업 절차

이 저장소에서 일하는 모든 AI(Claude Code, Codex)와 팀원이 따르는 절차.

## 1. 문서 지도

| 문서 | 용도 | 누가 바꾸나 |
|---|---|---|
| `docs/requirements.md` | 과제가 요구한 것 | 사람만 |
| `docs/design.md` | 설계, 확정/미정 결정 목록 | AI는 `제안:` 추가. `확정`은 사람이 고른 것을 날짜·결정자와 함께 적을 때만 |
| `docs/tasks.md` | 작업 단위, 의존성, 완료 기준 | AI·사람 (상태 변경, 하위 작업 추가) |
| `docs/status.md` | 현재 상태 + 인계 기록 | 세션 끝날 때마다 갱신 |
| `docs/learning.md` | 학습 확인 노트 | 사람만 답을 적는다 |
| `docs/workflow.md` | 이 문서 | 사람만 |
| `harness/` | 검증 루프 스크립트와 지시문 | 사람만 (작업 기준 파일이 허용할 때 예외) |
| `reviews/` | 검증 결과·수정 기록 | 루프 또는 수동 검증 시 추가 (지우지 않음) |

`requirements.md`, `workflow.md`, `harness/`는 사람이 특정 작업에 한해 허용했을 때만 AI가 수정한다. 허용 범위는 그 작업의 `harness/criteria/<작업ID>.md`에 적는다.

읽는 순서: `status.md` → `tasks.md`(현재 작업) → `design.md`(관련 절) → 필요하면 `requirements.md`

## 2. 역할과 판단 범위

### 역할
`[확정]` (D16) Claude Code가 구현·수정, Codex가 검증한다.
- 연결은 `harness/`로 한다. 실행법·종료 코드는 `harness/README.md`
- 결과는 `reviews/<작업ID>/run-<시각>/review-N.md`, 수정 기록은 같은 폴더 `fix-N.md`
- 검증 결과 마지막 줄 `VERDICT: PASS | FAIL | BLOCKED`, 수정 기록 마지막 줄 `STATUS: DONE | BLOCKED`
- 수정·재검증은 최대 2회. 그래도 FAIL이면 사람에게 넘긴다

### 사람이 정하는 것 (design.md 결정 목록 D 항목)
- 요구사항 해석, 범위 추가·삭제
- 모듈 사이에 공유되는 데이터 구조와 공개 함수의 이름·인자·반환 (예: VNode 구조, diff 결과 형식)
- 사용자에게 보이는 동작 (화면 구성, 버튼 동작, History 정책 등)
- 언어·도구·의존성·실행 방식·폴더 구조
- 이미 확정된 결정을 바꾸는 것

### AI가 정해도 되는 것 (멈추지 않음, 기록 불필요)
- 모듈 내부의 변수·헬퍼 함수 이름과 분리 방식
- 공개 계약을 바꾸지 않는 내부 알고리즘 세부
- 테스트 케이스 구성, 주석

애매하면 사람이 정하는 것으로 본다.

### 사람 결정이 필요한데 미정일 때
- 작업 상태를 `보류`로 바꾸고, D 항목에 선택지와 `제안:`을 적고, 사람에게 묻고 멈춘다.
- 임시 구현으로 진행하지 않는다.
- 하네스 루프 안이면 수정 기록을 `STATUS: BLOCKED`로 끝낸다.

## 3. 한 작업의 사이클

```
① 작업 선택 → ② 결정 절차(필요할 때) → ③ 구현 → ④ 검증 ⇄ ⑤ 수정
   → ⑥ 학습 확인(해당 시) → ⑦ 상태·인계 기록 → ⑧ 커밋
```

### ① 작업 선택
- `tasks.md`에서 아래를 모두 만족하는 작업 **하나**를 고른다.
  - 상태 `대기`
  - 선행 작업이 모두 `완료`
  - 필요 결정이 모두 `확정`
- 필요 결정 중 미정이 있으면 ② 결정 절차를 먼저 하고, 그 결정이 확정된 뒤 시작한다.
- 시작하면 `진행 중`으로 바꾸고 `status.md`를 갱신한다.

### ② 결정 절차
결정 작업(T00, T02, T18 등)과, 다른 작업의 필요 결정이 미정일 때 쓴다.
1. AI가 `design.md` 결정 목록과 관련 절에 선택지, 장단점, `제안:`을 적는다.
2. 사람이 고른다.
3. 결정 목록 상태를 `확정(날짜, 결정자)`로 바꾸고, 본문에 `[확정]`으로 옮긴다. 사람이 직접 하거나, 사람이 고른 내용을 AI가 그대로 옮긴다.
4. 결정 작업은 산출 결정이 모두 확정되면 ④ 검증(문서 방식)으로 넘어간다.

### ③ 구현 (Claude Code)
- 작업 범위 밖의 파일은 건드리지 않는다.
- 판단 범위는 2절을 따른다.
- 완료 기준에 맞는 테스트를 같이 작성한다.

### ④ 검증 (Codex, 또는 사람)
작업 유형에 맞는 방법으로 **직접** 확인한다.

| 유형 | 검증 방법 |
|---|---|
| 구현·설정 | 테스트 명령을 실행하고 명령과 결과를 적는다. 화면 작업은 브라우저에서 확인한 시나리오를 적는다 |
| 문서 | 일관성(문서 간 규칙 충돌), 상호 참조(언급한 ID·파일·절이 실제로 있는지), 시나리오 점검(문서만 보고 절차를 따라갈 수 있는지)을 하고 한 일을 적는다 |
| 결정 | 문서 검증 + 결정 목록 상태와 본문 `[확정]`이 일치하는지, 날짜·결정자가 있는지 |

공통 확인: 완료 기준 한 줄씩, 요구사항 ID 충족, 미정 사항을 몰래 확정하지 않았는지, 범위 밖 변경이 없는지.

검증 결과에 반드시 남길 것:
- 검증 대상 버전: 커밋 해시 + 커밋 안 된 변경 유무 (하네스는 스냅샷 해시를 자동 기록)
- 검증자, 수행한 검증, 기준별 판정, 마지막 줄 `VERDICT`

### ⑤ 수정과 재검증
- 검증에서 나온 FAIL만 고친다. 고친 뒤 반드시 ④를 다시 한다.
- **검증 결과의 무효**: 검증 이후 검증 대상 파일이 하나라도 바뀌면(수정, 리베이스, 다른 브랜치 병합 포함) 그 결과는 무효다. `완료` 처리와 커밋 전에 최신 버전으로 다시 검증한다.
  - 예외: ⑦에서 `tasks.md` 상태 칸과 `status.md`만 갱신하는 것은 재검증하지 않는다.
- 수정·재검증 최대 2회. 그래도 FAIL이면 사람에게 넘긴다.

### ⑥ 학습 확인 (사람)
- `tasks.md`의 학습 칸이 `해당 없음`이면 건너뛴다.
- 학습 칸에 절이 있으면, 검증 통과 후 상태를 `학습 확인 대기`로 둔다.
- 사람이 `learning.md` 해당 질문에 **자기 말로** 답을 적고 체크한다. 막히면 AI에게 설명을 요청한 뒤 다시 자기 말로 고쳐 적는다.
- AI는 학습 체크를 하거나 학습 확인을 대신 판정하지 않는다. 사람이 체크를 끝냈다고 알린 뒤에만 `완료`로 바꾼다.

### ⑦ 상태·인계 기록
- `tasks.md` 상태를 갱신한다.
- `status.md` 현재 상태를 덮어쓰고, 인계 기록을 템플릿대로 맨 위에 추가한다.

### ⑧ 커밋
- `[확정]` 각자 자기 브랜치에서 작업하고 커밋·푸시도 거기에만 한다. main에는 직접 푸시하지 않는다. (D19)
- `[미정]` main에 무엇을 어떻게 올릴지(비교 기준, PR 여부)
- 커밋은 최신 버전의 검증이 PASS인 상태에서 한다.

**브랜치 이름**: `<type>/<작업ID>-<짧은-설명>` (소문자, 단어는 `-`로 연결)
- 예: `docs/T00-workflow-setup`, `feat/T03-dom-to-vnode`, `fix/T06-patch-text-node`, `test/T10-phase1-edge-cases`
- 작업 하나 = 브랜치 하나가 기본. 작은 작업 여러 개를 묶을 땐 대표 ID 사용

**커밋 메시지**: Conventional Commits — `<type>(<작업ID>): <요약>`
- 예: `feat(T03): DOM을 VNode로 변환하는 함수 추가`
- 작업 하나당 커밋 하나가 기본, 필요하면 나눠도 됨

**type 목록**
| type | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 변경 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `style` | CSS, 포맷팅 |
| `chore` | 설정, 의존성 등 기타 |

## 4. 작업 상태 전환

| 상태 | 들어가는 조건 | 다음 |
|---|---|---|
| `대기` | 처음 | ① 시작 조건 충족 → `진행 중` |
| `진행 중` | ① 선택 | 구현·결정 끝 → `검증 중` / 사람 결정 필요 → `보류` |
| `검증 중` | ④ 시작 | PASS + 학습 해당 → `학습 확인 대기` / PASS + 학습 해당 없음 → `완료` / FAIL → ⑤ 후 다시 `검증 중` / BLOCKED → `보류` |
| `학습 확인 대기` | 검증 PASS, 학습 칸에 절 있음 | 사람이 학습 체크 완료를 알림 → `완료` |
| `보류` | 사람 결정 필요 | 결정 확정 → `진행 중` (이전 검증 결과는 무효) |
| `완료` | 위 조건 | — |

## 5. 공통 금지 사항
- 허용받지 않은 `requirements.md`, `workflow.md`, `harness/` 수정
- 미정 결정을 확정처럼 문서나 코드에 쓰기, 임시 구현으로 진행하기
- 외부 프레임워크(React, Vue 등) 사용 (R-TECH-02)
- 작업 유형에 맞는 검증(④) 없이 완료 처리
- 무효가 된 검증 결과로 완료 처리하거나 커밋
- AI가 학습 확인을 대신 체크하기
- 세션을 끝낼 때 `status.md` 갱신 안 하기

## 6. 플러그인과의 관계
- oh-my-claudecode, Superpowers 같은 플러그인을 써도 **기준 문서는 `docs/`**다.
- 플러그인이 별도 계획/스펙 파일을 만들면, 그 내용을 `tasks.md`와 `design.md`에 반영한 뒤 진행한다.
