문서 작업 (+ 검증 루프 스크립트). 미니 리액트 기능 코드는 대상이 아니다.

- `docs/requirements.md`는 과제 원문의 의미를 바꾸지 않는다

## 검토 기준
각 항목마다 문제가 있는지 판단하고, 근거 위치(파일:줄)를 적는다.

| ID | 기준 | 확인할 것 |
|---|---|---|
| C1 | 결정 작업의 시작 절차와 T02의 자기 의존성 | 결정 자체가 목적인 작업(T00, T02 등)을 절차대로 시작할 수 있는지. 선행 조건이 자기 자신의 산출물을 요구하는 순환이 없는지 |
| C2 | 선행 작업과 선행 결정의 구분 | 작업 의존성과 결정 의존성이 구분되는지, 작업 선택 규칙이 둘 다 판단하는지, 실제 실행 순서(T00a 부트스트랩, Hook 간 런타임 의존 등)와 맞는지 |
| C3 | 학습 확인 대기 상태와 해당 없음 처리 | 학습 확인이 끝나기 전 상태를 표현할 수 있는지, 학습 질문이 없는 작업을 어떻게 처리하는지, AI가 사람의 학습 확인을 대신 판정하지 않는지 |
| C4 | 사람의 설계 결정과 AI의 내부 구현 판단 범위 | 사람이 정할 범위와 AI가 정해도 되는 범위의 기준이 있는지, 서로 모순되는 예외 규칙이 없는지 |
| C5 | T08 이전의 History 설계 결정과 완료 기준 | History 구조 결정(D09)이 T08 시작 전에 필요하도록 되어 있는지. T08·T09 완료 기준이 초기 기록, 이전 스냅샷 보존, 뒤로 간 뒤 Patch를 다루는지 (정책 자체는 사람이 정함) |
| C6 | 검증 대상 코드 버전 및 변경 후 재검증 | 검증 결과에 검증한 버전이 남는지(수동 검증 포함), 인계 기록에 버전·담당이 있는지, 검증 후 변경 시 결과 무효·재검증 규칙이 있는지 |
| C7 | 문서 작업에 맞는 검증 방식 | 공통 규칙이 코드 테스트만 요구하지 않고, 문서 작업의 검증 방법과 기록 방식이 일관되게 있는지 |
| C8 | 검증 루프 실행 제어 (`reviews/harness-review.md` H1–H4) | CLI 실패를 성공으로 받지 않는지, VERDICT를 엄격히 해석하는지(없음/중복/마지막 줄 아님 → 실행 오류), BLOCKED 상태로 멈추는지, 스냅샷이 경로·모드·삭제를 구분하는지. 가짜 codex/claude로 재현 가능하면 재현한다 |

## 판정 규칙
- 기준별: `PASS` / `FAIL` / `BLOCKED` (정의는 `harness/prompts/verify.md`)
- 이후 작업에서 정할 결정이 `[미정]`과 결정 목록에 기록돼 있으면 PASS
- 기준 밖에서 발견한 문제는 "기타 발견"에 따로 적는다. 심각한 모순이 아니면 판정에 반영하지 않는다
